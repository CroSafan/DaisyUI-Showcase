# DaisyUI Enterprise Showcase

A 31-page, server-rendered reference application showing how DaisyUI can support business software with Spring Boot and JSP. The home page links to every demonstration; the persistent shell provides category navigation, a mobile drawer, and an application-wide theme selector. Ten connected pages form a deeper Time Management workspace. The application form example opens in its own full-width shell.

The showcases are grouped into **Foundations (6)**, **Business applications (6)**, **Enterprise solutions (9)**, and **Time management (10)**. The route index below lists all 31 pages, followed by a detailed guide to what each page displays and what visitors can try.

**Node.js, npm, Yarn, pnpm, and other frontend package managers are not required.** There is no frontend compilation or JavaScript build step.

## Stack and requirements

- Java 17 or newer
- Maven 3.9 or newer
- Spring Boot 3.5.16, Spring MVC, Jakarta JSP, Jakarta JSTL, and Bean Validation
- DaisyUI 5 browser-ready CSS, committed under `src/main/resources/static/css/`
- Plain CSS and a small amount of vanilla browser JavaScript

No database, account, API key, CDN request, or Node runtime is needed to run the application. Sample business records are deterministic and generated by `ShowcaseService` and `TimeManagementService`.

## Build and run

```sh
mvn clean verify
java -jar target/daisyui-showcase.war
```

Open [http://localhost:8080/](http://localhost:8080/). During development, `mvn spring-boot:run` also works. To change the port, add `--server.port=8081` to the `java -jar` command.

The project uses **WAR packaging** because Spring Boot does not support JSP rendering from an executable JAR. The Spring Boot Maven plugin produces an executable WAR that can run with `java -jar`; `DaisyShowcaseApplication` also extends `SpringBootServletInitializer` for deployment to a compatible external Jakarta servlet container. JSPs remain under `WEB-INF/jsp`, so they cannot be requested directly.

## Languages

The application supports Croatian and English, with Croatian selected by default. The header language picker reloads the current route with a `lang` parameter while preserving other filters; Spring's locale interceptor saves the choice in a cookie. JSP views render messages directly with Spring's `<spring:message>` tag and the `MessageSource` bundles in `src/main/resources/i18n/messages.properties` (English) and `messages_hr.properties` (Croatian). JavaScript does not rewrite page text after loading.

The `/error` view uses a separate Enterprise-styled shell for 404, 403, server, and other errors. It displays the HTTP status and escaped requested path, with links back to the showcase. Direct visits to `/error` display the 404 design, and missing routes keep their 404 response status.

## Project layout

| Location | Purpose |
| --- | --- |
| `src/main/java/com/example/daisyshowcase/controller/` | Routes, filters, pagination, form handling, and time workflow actions |
| `src/main/java/com/example/daisyshowcase/service/` | Page catalog, sample data, and computed time ledgers |
| `src/main/java/com/example/daisyshowcase/model/` | Page, metric, record, and validated form models |
| `src/main/webapp/WEB-INF/jsp/` | Protected JSP views and shared fragments |
| `src/main/resources/static/css/` | Local DaisyUI, theme, application, and time workspace stylesheets |
| `src/main/resources/static/js/` | Plain JavaScript for theme persistence and demo interactions |
| `src/test/` | Spring MVC route, data, and validation tests |

Spring MVC resolves view names with `/WEB-INF/jsp/` as the prefix and `.jsp` as the suffix. Most JSP pages use Jakarta JSTL (`jakarta.tags.core` and `jakarta.tags.functions`) for navigation, iteration, conditions, and escaping. Shared fragments provide the main showcase shell, title, metrics, record table, insight panel, dialog, and footer. The standalone application form has its own header and section navigation. The Spring form tag library binds and displays validation results on the forms page. JSPs contain no Java scriptlets.

## DaisyUI without a frontend toolchain

The repository includes browser-ready `daisyui.css` and `themes.css` from DaisyUI 5. Spring Boot serves them as static resources. Application CSS supplies responsive page composition and a few visual refinements while DaisyUI supplies components, semantic colors, and theme tokens. The browser does not need Tailwind's runtime, a remote font, or any JavaScript package manager.

Every page uses the HTML `data-theme` attribute. Theme selectors write the selected name to `localStorage`, update the document immediately, and restore it before styles render on the next page. Available themes are Light, Dark, Corporate, Enterprise, Business, Black (high contrast), Synthwave (creative), Neutral, and Cupcake (colorful). The ERP and CRM examples open in Enterprise by default. The standalone application form has its own theme selector and shares the saved preference.

The default scenario is September 2026, with 14 fictional employees across Operations, Product, and Support. Monthly clocking cells, totals, timesheets, and reports are derived from the same Java service. The department matrix includes weekends, paid leave, a fictional company closure, overtime, missing punches, and late arrivals. Month and team filters recompute the ledger on the server. CSV exports use the same totals displayed on screen.

Clocking events, correction requests, leave requests, and approval decisions are stored **only in the current demo session**. A submitted leave request or correction appears in the approvals queue, and decisions appear back on its source page. These actions do not alter the deterministic payroll ledger or persist after the session ends. The holiday calendar is fictional and is not legal or payroll guidance.

The business actions outside the form and data filter are **UI demonstrations**; they display local feedback and do not persist records. The healthcare page uses obviously fictional patients. Charts and routes use HTML/CSS, with no charting or mapping library.

## Detailed showcase catalog

### Foundations

1. **Component gallery — `/showcase/components`**: A reference for buttons, badges, alerts, tabs, collapses, dropdowns, statistics, avatars, loading states, progress, breadcrumbs, cards, lists, tables, and dialogs. Its form section demonstrates decimal and whole-number fields, percentage input, fixed left-side currency symbols for EUR, USD, and GBP, and a multi-choice department dropdown with a live selection count.
2. **Theme laboratory — `/showcase/themes`**: Nine selectable visual themes with live color swatches and a customer overview preview. Changing the theme updates the shared shell and semantic component colors immediately and saves the choice in browser storage. The Enterprise option emphasizes compact, neutral surfaces.
3. **Responsive laboratory — `/showcase/responsive`**: Phone, tablet, and desktop composition examples beside a resizable page layout. Narrow widths turn navigation into a drawer, stack cards and forms, and keep wide tables scrollable inside their panels.
4. **Forms and validation — `/showcase/forms`**: A project request form with name, email, department, budget, description, and urgency. Spring MVC validates submissions and displays field errors or a confirmation. A second panel displays success, warning, error, read-only, disabled, date, and password input states.
5. **Application form workspace — `/showcase/workspace-form`**: A separate supplier onboarding layout without the showcase sidebar, linked as the last option in the main sidebar. At 1,920px viewport width it uses a centered 1,600px canvas, a 300px local navigation and a 1,300px content column, including each column's internal padding. Smaller screens reduce outer margins; tablet navigation becomes a horizontal section bar; phone fields stack in one column. Its header offers all nine themes. Six sections demonstrate text, search with suggestions, email, URL, phone, number, decimal money with a fixed left currency symbol, percentage, date, time, date-time, month, week, color, range, multiple selection, radio, checkbox, toggle, file and password inputs. Native validation, live summary, file names and a session-only draft are interactive; demo submission does not send data to the server.
6. **Data management — `/showcase/data`**: A 42-record customer queue with server-side name/ID search, status filtering, ten-record pages, and an empty state. Select-all and per-row checkboxes update the selected count; row details open a dialog. Create, edit, and bulk buttons are demo feedback actions.

### Business applications

7. **Analytics dashboard — `/showcase/analytics`**: Revenue, customer, conversion, and NPS metrics; a 12-month performance chart; regional records; and a recent-signal feed. It illustrates how summary measures, trends, and supporting records can sit in one dashboard.
8. **CRM workspace — `/showcase/crm`**: An Enterprise-themed account portfolio with text search and health filtering. The page also shows an Acme Industries account summary, next actions, and a compact opportunity-stage table. Row buttons open the shared detail dialog.
9. **ERP operations — `/showcase/erp`**: An Enterprise-themed purchasing queue with search and status filtering. Exception lists, function capacity, and warehouse stock and movement tables place procurement, production, and fulfillment details in one dense workspace.
10. **Finance and accounting — `/showcase/finance`**: Cash, revenue, receivables, and payables metrics; recent transactions; department spending progress; and a receivables/payables comparison. The approval button demonstrates local UI feedback.
11. **People and HR — `/showcase/hr`**: Headcount, roles, leave, and engagement metrics alongside an employee spotlight, a people calendar, and a directory-style record table. This page presents common people-operations information in one view.
12. **Project workspace — `/showcase/projects`**: Sprint metrics, a task board spanning backlog through review and done, project records, and milestone context. It demonstrates task priority, ownership, and delivery state at a glance.

### Enterprise solutions

13. **IT service desk — `/showcase/itsm`**: Incident and SLA metrics, a selected VPN incident, investigation history, and a ticket queue. The page shows how priority, owner, response target, and timeline context fit together; the comment control is a demo action.
14. **Cloud operations — `/showcase/cloud`**: Service and instance metrics, CPU/memory/storage utilization bars, deployment activity, a log preview, and a service inventory. It combines resource health with recent release context.
15. **Security operations — `/showcase/security`**: Posture metrics, a privileged sign-in incident, a detection timeline, and investigation records. Severity and state badges support triage; the investigation button is a demo action.
16. **Commerce admin — `/showcase/ecommerce`**: Sales and order metrics, catalog-health cards for products to watch, and a recent-order table. Low-stock signals and fulfillment states are visible together; the product-management button shows demo feedback.
17. **Supply chain tower — `/showcase/logistics`**: In-transit and on-time measures, a Zagreb-to-Munich route view, warehouse movement, shipment records, and a delivery exception. It illustrates location and timing context without a map library.
18. **Care administration — `/showcase/healthcare`**: Fictional appointments, check-in state, room capacity, staff-on-duty metrics, a daily appointment flow, and department/room availability. All patient names are explicitly fictional.
19. **Subscription admin — `/showcase/saas`**: MRR, account, trial, and churn measures plus plan cards, a subscription portfolio, and entitlement context. Plan and upgrade buttons demonstrate the component states without changing billing data.
20. **Approval center — `/showcase/approvals`**: A network equipment request with risk, amount, reviewer comment, decision buttons, delegation, and a decision trail. Approve/reject changes the displayed demo status only; it does not submit a business approval.
21. **Executive command — `/showcase/executive`**: Company-wide revenue, customers, margin, and employee NPS, with trajectory, risk briefing, and customer, people, and technology signals. It brings cross-functional measures into a single leadership view.

### Time management

22. **Time command center — `/time/overview`**: Workforce readiness, attendance totals, an attention queue, upcoming absences, and links to the connected time workflows. Start here to understand the sample month.
23. **Time access — `/time/access`**: A self-service terminal with clock-in, break start/end, and clock-out controls. Valid state transitions add timestamped events to the current server session, and the page displays the resulting audit trail.
24. **My timesheet — `/time/timesheet`**: Employee selection, a full-month daily ledger, paid hours, breaks, leave, and exceptions. A correction form records a request in the current session and sends it to Time approvals for review.
25. **Department clockings — `/time/department`**: A whole-department month matrix containing every employee and calendar day, daily totals, and employee totals. Month and team filters recalculate the ledger, and CSV export uses the same totals shown on screen.
26. **Shift planning — `/time/schedules`**: A seven-day coverage board with early, core, and late shifts. Week and team controls change the schedule; open slots, handovers, and planning notes call out coverage gaps.
27. **Leave management — `/time/leave`**: Personal entitlement, team coverage forecast, a leave request form, and a cross-team register. New requests live in the current session and appear in the manager approval queue; decisions return to the register.
28. **Holiday calendar — `/time/holidays`**: An illustrative register of observed days and company closures, calendar assignment, entitlement categories, and the effect of a September closure on the sample ledger.
29. **Time approvals — `/time/approvals`**: A manager inbox for leave, clock corrections, overtime, and shift swaps. Approve and reject actions are saved in the session and reflected on related request pages.
30. **Attendance exceptions — `/time/exceptions`**: Team and severity filters over missing punches, late arrivals, and overtime anomalies. A selected exception shows investigation context and the suggested resolution sequence.
31. **Time reports — `/time/reports`**: Paid-hours trend, team comparison, attendance and absence measures, and exception counts. Month and team choices update the report, and a CSV export provides the displayed team's ledger totals.

### How the demonstrations behave

- **Saved preferences:** The language choice uses a locale cookie; the theme choice uses browser storage. Croatian is the default language; ERP and CRM open in the Enterprise theme.
- **Server-driven examples:** The form validation, data queue filters and pagination, and Time Management month/team/week filters are handled by Spring MVC.
- **Session workflows:** Clock events, correction and leave requests, and time-approval decisions last for the current server session. They are examples, not a payroll or attendance system.
- **Display-only controls:** Most buttons on the other business pages show a toast or local state change. Their sample records are deterministic and are not saved to a database.

## Accessibility and responsiveness

Navigation is keyboard accessible, has a skip link, and marks the active page. Form controls have labels and validation text. Tables have headers, important states include text as well as color, and dialogs use the native `<dialog>` element. Data tables scroll within their panels on narrow screens; the overall page should not scroll horizontally. The sidebar becomes a mobile drawer below 880px.

## Verification

`mvn clean verify` compiles the WAR and runs MVC tests for all 31 page routes, data filtering, valid/invalid form submissions, time-ledger reconciliation, session clocking, leave requests, approvals, and CSV export. For a runtime check, start the packaged WAR and visit the home page and any showcase route. The packaged views, local CSS and JavaScript, and JSTL are served from the WAR. The repository contains no `package.json`, Node modules, frontend build pipeline, Thymeleaf dependency, or Thymeleaf templates.
